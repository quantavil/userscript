## 1. Chess.com moves were confirmed against optimistic local state

### Symptom reported

User: with auto move on, the bot "appears to move" but may not actually be moving; opponent looks frozen.

### Root cause (measured, not inferred)

Drove a live guest bot game on chess.com and called `controller.move({from:'e2',to:'e4'})`, sampling the controller before/after:

| | `getFEN()` | `getTurn()` | `getHistorySANs()` | `getHistoryFENs()` |
|---|---|---|---|---|
| before | start pos | 1 | `[]` | `[startPos]` len 1 |
| **sync after `move()`** | **after e4** | **2** | **`["e4"]`** | `[afterE4]` len 1 |
| +4s … +25s | unchanged | 2 | unchanged | **len 1, never grows** |

Also measured: `getState()` returns `"Idle"` immediately after `move()`, so the `settled` gate in `read()` protects nothing.

Three facts combine into the bug:

1. **`getHistoryFENS()` is not a ply history.** It holds only the current position; length stays `1` regardless of moves played. The code assumed root-at-index-zero (`sites/types.ts`: *"Canonical accepted FENs indexed by ply, with the root at index zero"*), so `confirmedFens[ply]` was always `undefined`.
2. **`getFEN()` / `getTurn()` / `getHistorySANs()` all flip synchronously inside `move()`**, before any server call.
3. **The true root exists only at `getFingerprints().startingFen`** (verified correct for the standard position; also correct for from-position games).

Causal chain of the old code:

```
readPositionHistory() treats getHistoryFENS()[0] as the root
  -> it is actually the current position, so replaying the SANs from it fails
  -> snapshot.history = { startFen: <current position>, moves: [] }
  -> requestPly() = 1
  -> confirmSiteMove(): confirmedFens[1] is undefined -> wait -> 1s timeout
  (and because history was malformed, expectedPly could fall to null,
   taking the getFEN() fallback, which the optimistic flip satisfies instantly)

net: every Chess.com move could report "confirmed" on local state alone
```

**Scope correction:** the move itself *does* land. The probe showed `1. e4` in the site's move list and a valid `getPGN()`. This was a **confirmation-signal** bug, not a submission failure. Do not go looking for a transport bug.

### Fix

Rebuild the history by replaying accepted SANs from the fingerprint root — the same `replaySanLine` path the Lichess and PyChess adapters already use — so `confirmedFens` keeps its documented root-at-index-zero shape.

- `src/sites/chesscom-state.ts` — added `getFingerprints?()` to `ChessGame`, added `getStartingFen()`.
- `src/sites/chesscom.ts` — new `readChesscomHistory()`; `read()` now uses it for both `history` and `confirmedFens`.
- Returns `undefined` when the root or SAN list is missing, so a snapshot never advertises history it cannot back with real plies.

### To validate

```bash
bunx vitest run tests/chesscom-history.test.ts   # 5 tests
```

`tests/chesscom-history.test.ts` encodes the measured semantics verbatim (length-1 `getHistoryFENs`, fingerprint root, SAN list). Key case: *"never exposes a ply-indexed slot that the accepted SAN list cannot back"* — controller already flipped locally but SAN list empty must yield `confirmedFens.length === 1` and `confirmedFens[1] === undefined`.

### Not verified

No live Chess.com round was played with the fix installed. **A manager-installed build still needs one live game to confirm**, per the existing browser-check procedure. If `getHistorySANs()` turns out to lag unpredictably on real rated games, confirmation will now honestly report `Move was not confirmed` and retry rather than silently pass — that is the intended failure mode, but it will look like a regression until verified.

### Reviewer notes

- `readPositionHistory()` in `src/history.ts` is now **dead production code** (only `tests/history.test.ts` uses it). Knip does not flag it because tests are entry points. Consider deleting it plus its test.
- `getHistoryFENS()` is now unused. `getHistoryFENs?()` remains on the `ChessGame` interface only.

## 2. T1 game report

New module `src/report/` (359 lines), plus a `Game report` settings toggle (default on).

| File | Lines | Contents |
|---|---:|---|
| `accuracy.ts` | 112 | `winPercent`, `moveAccuracy`, `classifyByLoss`, `classifyPhase`, `readMaterial`, `CPL_CAP` |
| `aggregate.ts` | 87 | `buildGameReport()` → per-player accuracy/ACPL/counts/phase split |
| `analyzer.ts` | 160 | background engine pass, `runGameReport` / `cancelGameReport` / `resetGameReport`, `gameReportSignal` |

**Deliberate decisions to check:**

- **Lichess open formulas, not Chess.com's.** `winPercent = 50 + 50*(2/(1+exp(-0.00368208*cp)) - 1)`, `moveAccuracy = 103.1668*exp(-0.04354*(wpBefore-wpAfter)) - 3.1669`. Chess.com's is proprietary. Panel labels output "Local engine estimate". Max of the curve is 99.9999, not 100.
- **POV handling.** `before` is already the mover's view (mover is to move). `after` comes from the position the move produced, where the *opponent* is to move, so it is negated. Getting this backwards inverts every verdict — `tests/report-analyzer.test.ts` has three tests that pin it.
- **Runs only when `snapshot.phase !== 'live'`** (`src/ui.ts` `updateDisplay`). It shares the single serialized UCI client (`engine/uci-client.ts` queue) with move search and must never contend with it.
- **Fixed depth 16 / 350 ms**, NOT `BotState.botPower` / `BotState.moveTime`. The live budget is tuned to stop early under a clock and is too shallow to separate an inaccuracy from a mistake. Do not "unify" these.
- **Searches each position once**, then pairs evaluations afterwards, rather than two searches per ply.
- **`classifyPhase` tests the opening by move number first**, before any structural endgame test, so an early queen trade cannot mislabel moves 1–10. Unreached phases report `null`, rendered as `—`.
- `readMaterial` skips FEN run-length digits and `/`. A first draft counted digits as black pieces; covered by *"reads an empty board as no material"*.

**Known cosmetic issue:** `readMaterial` counts every non-king piece including pawns, so a full start position is 15/15, not 14/14. Thresholds (`material <= 10`, `material <= 14 && stripped <= 4`) were checked against that.
